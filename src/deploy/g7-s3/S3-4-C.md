## Offline receipt binder — synthetic code semantics

Code: \`src/server/g7-operational/s3-4-c.ts\`:
\`assessS34COwnerManagedBinding(raw, trustedLocalPublicKeys, onsiteClockUtc)\`.
\`s34CSigningBytes(raw)\` supplies a deterministic Ed25519 statement for
**local** pre-authorized Owner/QA signers only. There is NO automatic
filesystem/network access and NO private-key generation or IO in the module.

Input stays entirely on the restricted machine:
- \`scope=G7-S3-4C-OWNER-MANAGED-OFFLINE\`, \`schemaVersion=1\`.
- \`evidence\`: complete S3-4-B2-5 privately reviewed packet (17/17 PASS).
  Matching supplied evidence is not genuine source authentication.
- Exactly 17 \`receipts\` with \`name\` (S3-4-A check), \`evidenceId\`,
  \`sha256\` (lowercase 64 hex) and \`bytes\` (non-empty Uint8Array or Buffer,
  <= 64 KiB). These are **small on-site verification receipts**, NOT the
  full backup/CAD/S3 bytes. Owner must independently check actual source
  and generate/retain the receipts on-site.
- \`ownerApproval={ownerId:"OWNER-...",signedAtUtc:"...Z"}\`;
  \`qaApproval={reviewerId:"QA-...",signedAtUtc:"...Z"}\` matching B2-5;
  \`expiresAtUtc\` no more than 24 hours after the later signature, and
  an on-site trusted clock argument. Both review times follow B2-5 review,
  precede \`nowUtc\` and are not expired. This is receipt-signature freshness,
  NOT an S3-5 operating window.
- \`signatures={owner:"<canonical Ed25519 Base64 signature>",
  qa:"<canonical Ed25519 Base64 signature>"}\` of the exact bytes returned
  by \`s34CSigningBytes\`. Statement binds SHA-256 of the entire supplied
  B2-5 packet, Source/rollback revision, Snapshot, Epoch, CR, Schema,
  four distinct immutable digest claims, signer identities and times,
  expiry, and all seventeen \`[name,evidenceId,receiptSha256]\` references.
- Local approved trust anchors are provided separately, out of the input:
  two **distinct Ed25519 public keys** for Owner and QA. The code rejects
  same keys, private keys, wrong key types, wrong/missing signatures,
  swapped identities, invalid/missing/duplicate/checkpoint/receipt bytes
  and invalid UTC windows. The program CANNOT verify that keys were
  enrolled by the site authority; the Owner must validate that locally.
  Separate cryptographic keys do NOT by themselves prove distinct humans.

Result is restricted to public-safe fixed **state/reason codes and count**,
with no names, evidence IDs, digests, signatures, paths, keys or bytes:
- \`BLOCKED\`: failed/malformed/forged/expired/invalid proof structure.
- \`PENDING\`: S3-4-B2-5 source packet has genuine \`NOT_RUN\` checks.
- \`LOCAL_SIGNED_RECEIPTS_CONSISTENT_NOT_SITE_GO\`: actual receipt bytes
