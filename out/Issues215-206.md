## R215 / ADR-215 — 서버 근거 상태의 공통 표시

전역 헤더 맨 오른쪽과 Viewer 자체 메뉴 맨 오른쪽에 공통 상태 표시를 둔다. 일반 Viewer에서는 시각적 중복을 최소화하고 immersive/native fullscreen에서는 Viewer subtree 안에서 접근 가능해야 한다. 기존 계정 링크 목적지 `/g7-runtime`, 도면 목록/기준정보/등록/운영 로그/버전을 보존한다.

| 서버 관측 | 표시와 동작 |
| --- | --- |
| 최초 또는 재검증 중 | 확인 중; 이전 로그인 완료를 확정 상태로 유지하지 않음 |
| status ACTIVE + authEnabled true, session200 및 유효 ACTIVE actor | 로그인됨 + allowlisted Admin/Editor/Reader 요약; 계정 링크 |
| ACTIVE + session401 | 로그인 필요; 계정 링크 |
| 명시적 OFF + authEnabled false | 인증 미사용, 비클릭; session 호출0 |
| BLOCKED / bootstrap 미완료 | 구성 대기 또는 인증 확인 불가, 비클릭 |
| status 실패/잘못된 DTO, session403/404/5xx/통신 오류/잘못된 actor | 인증 확인 불가, 비클릭; 낙관 로그인·익명 fallback 금지 |

상태 조회 소유자는 앱 수준 공통 provider/store 하나다. 두 표시가 각각 네트워크를 소유하지 않는다. status→session 순서, AbortController와 generation guard, unmount/StrictMode 정리, 이벤트 중복 병합을 구현한다. 내부 actor.id, CSRF, grant·session 원문은 표시 state/DOM/저장소/로그에 복사하지 않는다. 역할은 알려진 역할만 정규화하며 모르는 값/빈 역할에 거짓 역할을 만들지 않는다. 헤더는 인가 근거가 아니다.

조회 트리거는 초기·경로/도면 진입, 포커스 복귀·visible 복귀, 계정 로그인/로그아웃/초기·일반 비밀번호 변경·세션 재조회/회수 결과(성공·실패 모두)다. 클라이언트 갱신 신호는 payload 없는 invalidation일 뿐 서버 재조회를 대체하지 않는다. 다른 탭은 포커스/재표시에서 검증한다. 계정 변경/업무 요청의401도 안전하게 invalidation으로 연결할 수 있으나 조회 자체가 재조회 이벤트를 재귀 발생시키면 안 된다.

**idle 정책 결정:** 현재 `handleG3Request(session) → authenticate → createG3IsolatedStore`는 `last_seen_at`을 갱신한다. 이번에는 서버 검증/8h absolute·30m idle 정책을 바꾸거나 새 heartbeat를 만들지 않는다. 백그라운드·주기 polling·무조건 timer 재검증 없이 실제 사용자 진입/복귀/계정 이벤트만 사용하고 중복 요청을 합친다. 따라서 사용하지 않는 탭의 표시는 다음 사용자 복귀/관측까지 마지막 관측 상태일 수 있으며 실시간 회수 push를 주장하지 않는다. 장시간 비활성 뒤 focus에서는 기존 timeout으로401을 받아야 한다. **표시 때문에 주기적으로 idle이 연장되지 않음**을 요청 수와 기존 auth 회귀로 확인한다.

색상만으로 상태를 구분하지 않고 텍스트·명확한 accessible name·focus ring을 둔다. 화면마다 한 곳만 상태 변화를 polite하게 알리며 inert 전역 헤더와 Viewer의 경쟁 live region을 피한다. 320/390/768/1440px 및200% 확대에서 줄바꿈/요약형으로 overflow 없이 메뉴를 사용할 수 있어야 한다.

## R206 / ADR-206 — Canvas만의 브라우저 선호색

`보기 → 배경색 설정`의 단발 소형 dialog/popover를 Viewer fullscreen subtree에 배치한다. [ViewerPanelPolicy](ViewerPanelPolicy.md)의 독립 조회/작업 패널이 아니므로 DnD 대상이 아니다. 실제 ready DXF `three-dxf-viewer`에서만 활성화한다. dxf-viewer/DWG/fallback/loading/error는 구체적 disabled 사유를 표시한다. Picker(input color), 명암·유색 Palette, HEX 직접 입력/현재값, 기본 검정 복원을 제공한다. 유효 색은 즉시 반영하고 미완성/무효 입력은 오류로 알리며 마지막 유효색을 유지한다. Escape 한 단계·Tab·외부 클릭·focus 복귀·상위 modal 우선 및 Canvas 입력 분리를 기존 셸과 통합한다.

순수 색 검증/helper와 client preference hook을 분리한다. canonical `#rrggbb`만 versioned key `layoutManager.viewer.canvasBackground.v1`에 저장한다. 미설정/무효/접근 차단은 초기 `#000000`; 쓰기 실패는 현재 메모리 선택을 유지하되 저장되지 않았다고 알린다. 같은 origin/profile 전체 도면·새 탭·새로고침에 공통 적용하고 reset도 저장한다. client hydration 후 최초 Adapter 생성에 현재 값을 전달하여 첫 유효 렌더부터 적용한다. storage event는 유효값·삭제(default)를 동기화하고 읽기/쓰기 예외가 Viewer 로딩을 깨지 않게 한다.

CadViewerAdapter optional 배경 capability + ViewerManager 전달을 사용한다. 현재 값은 기존 Manager의 presentation 설정으로 보유하여 load/Renderer 전환 때 지원 Adapter에 mount 전 적용할 수 있다. 사용자 변경은 살아있는 renderer.setClearColor 및 render만 수행한다. 색 state를 load effect dependency에 넣지 않으며 Source GET/parse/Worker/GL context/canvas DOM/카메라/선택/Undo를 재생성하지 않는다. 미지원 adapter는 no-op 성공 표시하지 않는다.

**Material/Scene/export 경계:** 현 코드는 원본 검정 clone을 흰색으로 바꾼 뒤 tagImportedTree/exchangeBaseline/Scene serialization을 실행한다. 선호색을 그 canonical tree에 남기면 export·영속 Scene이 오염되므로 금지한다. canonical 원래 material 색과 renderer 소유 display clone의 역할을 분리한다. black-origin material만 배경 luminance 기반 검정/흰색 표시 보정하고 원래 유색은 유지한다. parse와 persisted Scene restore 양쪽에 동일 정책을 적용한다. export baseline·serializeSourceScene/Scene artifact는 **선호색과 무관한 canonical material**을 읽어야 한다. 안전한 방식은 원본 clone 색을 보존하고 실제 render 구간에만 owned material에 보정한 뒤 finally에서 복원하는 방식 또는 명확히 분리된 display clone tree다. 선택/강조 material 교체와 공유 cache dispose도 검토한다. 기존 Scene에 이미 저장된 흰색의 원래 검정 여부를 추측하여 전체 흰색을 변환하지 않는다. 이 과거 데이터 한계 및 임의 객체색과 배경 일치의 일반 대비 한계는 안내한다.

## 보완 설계 — 현재 검증 실행의 Recovery Docker 증거 (2026-11-12)

최초 동결 QA는 필수19개 중7 PASS / recovery-docker1 FAIL / 후속11 NOT RUN, stale=false다. 원인은 `recovery-local-docker.test.mjs`의 역사적 #281 image tag와0.61.1 alias/receipt 상수로, 현재0.62.0 package의 정상 `G7_AUTO_IMAGE_PAIR_INVALID` 차단을 유발했다. 제품 auth/image pair 정책 실패가 아니며 예전 image PASS 또는 검증 완화로 대체하지 않는다. 원래 run 및 실패 로그는 IssueEvidence/FailureLedger에 보존한다.

**Manager 설계 결정:** 기존 `docker-roles`를 현재 run의 유일한3-role build/검사 prerequisite로 재사용한다. manifest에서 `recovery-docker`를 그 뒤로 이동하며 recovery-only 위험도 docker-roles를 반드시 포함한다. release/combined에서 중복 build 항목을 만들지 않는다. Docker 미가용/build FAIL이면 recovery는 필수 NOT RUN이며 이전 이미지를 사용하지 않는다. dependency/order/모든 필수 항목 보존을 CLI 계약 시험으로 고정한다.

Recovery test는 `VERIFY_LOCAL_RUN_ID`와64hex `VERIFY_LOCAL_SOURCE_FINGERPRINT`를 엄격 검증하고 기존 builder와 같은 `cad-layout-viewer:vl-<run>-{app,migrator,worker}`만 선택한다. tag 이름만 믿지 않고 세 image의 role(app/migrator/cpu-worker), package version, 현재 Git HEAD revision, repository source, source-fingerprint 및 architecture를 docker inspect로 대조한 후 사용하는 이미지 ID를 결합한다. 누락/다른 run·version·role·revision·fingerprint는 fixture 생성 전에 fail closed. fixture app/migrator alias와 예상 receipt.sourceRelease는 현 package version에서 유도하되 기존 G7 validPair/서명/schema/호환 검사 자체는 변경하지 않는다. 작업 중 tag 바뀜을 피하도록 검증 image ID에서 nonce alias를 생성하고 실제 readback을 확인한다. 기존 historical image/tag는 변경·삭제하지 않는다.

직접 실행도 지원하되 숨은 과거 이미지 fallback 또는 암묵적 자동 build는 금지한다. `test:recovery-local:docker`의 prerequisite 오류는 현재 검증 run/env와 선행 `verify_local_docker.py --mode worktree` 필요를 안내하고, Operation에 같은 run ID·정확 source fingerprint로 builder→test를 실행하는 경로 또는 공식 verify:local 경로를 명시한다. 잘못된/missing env를 skip/PASS로 처리하지 않는다. focused fixture 검증과 최종 CLI 실행은 별도 기록한다.

**자원 소유/정리:** alias/tag/임시 root 생성·ensureAutomatedGreenfield를 포함한 모든 mutation을 try/finally 범위로 옮긴다. nonce-owned resources만 정리하고 실패 전에 생성한 alias 하나·디렉터리까지 제거한다. 처음 실패에서 남은 자원도 정확 nonce/이름을 확인한 후 정리하며 다른 run/운영 자원은 건드리지 않는다.
