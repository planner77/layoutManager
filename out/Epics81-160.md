## 교차 문제 A — 메모 스냅이 모호한 Scene ID를 신뢰함

**기존 코드 경로:** `collectMemoSnapCandidates`/ `nearestMemoSnap`은 각 대상의 유효 Scope만 확인하여 같은 `(origin,id)`의 복수 Geometry·Affine을 별개의 유효 대상처럼 취급할 수 있었다. `currentMemoSnapChoice`는 첫 대상, `MemoSessionSnapStore.snapshot`은 Map의 마지막 대상, `reposition`은 첫 대상을 선택한다. 동일 불변 식별자의 서로 다른 Target은 실제 도면에서 위치 오류 위험이 있다. 실제 현장 재현은 미확인.

**수정 계약:** 하나의 Scope에서 유효한 동일 `(origin,id)`가 둘 이상 발견되면 모든 해당 Target을 후보·최근접 스냅에서 제외, 선택 재검증을 실패시킨다. `uniqueMemoSnapTarget`는 Viewer의 연결 유지(KEEP) 동작에서 **서버 PATCH 전에** 임의 첫 Target을 선택하지 않도록 Scope/Origin/ID 유일성을 강제하고, PATCH 후 검증에도 사용한다. 기존 binding은 `lastWorld`에 동결/BROKEN, `reposition`은 변경 없이 에러. 유일한 원래 Target이 복구되면 같은 immutable ID만 정상 투영한다. Source/Generated를 서로 혼동하거나 브라우저 임시 관계를 서버 영속 Anchor로 승격하지 않는다. 100 Memo/20k point 상한과 자유 메모/Renderer fallback 유지.

## 교차 문제 B — Reset 조회 Snapshot ID의 중복

**기존 코드 경로:** `resetRows`는 입력 expected ID 중복을 차단했지만 `sameRevisionSnapshot`은 observed 쪽 ID 유일성을 검증하지 않았다. `expected [A@0,B@4]`, `observed [A@0,A@0]`은 길이 2, 각 revision 일치로 TRUE가 된다. 실제 단일 SQLite PK 조회가 중복이라는 증거는 없지만 계약이 DB query shape에 불필요하게 종속됐다.

**수정 계약:** expected·observed ID가 각각 유일한 상태로, 동일 ID와 Revision이 1:1이어야만 `SOURCE_ONLY/ALL`의 기존 원자 transaction을 허용. 기존 G7 권한, 같은 Site Editor 공동 EDIT 및 작성자/Site Admin DELETE, Version/Scene Revision/SHA, Soft Delete/Audit와 immutable DXF/SceneAsset은 그대로 유지.
